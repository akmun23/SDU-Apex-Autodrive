## Handoff checkpoint: active optimizer identified; transition mismatch quantified

Work Package G has a candidate with independent open-plane support, but its
practice promotion gate is not met. The only trusted practice data (P0) does
not exercise the candidate's gated region. No fresh racing validation has been
run, and the candidate must remain offline.

The P0 trajectory was generated by the custom AutoDRIVE v1.3 spatial
source-command optimizer at
`SDU_Apex_Autodrive_Exact_MinTime_Optimizer_v1_3/f1tenth_planning/autodrive_mintime/`,
not by the legacy global double-track optimizer. The active optimizer already
reads many production MPC constants from `mpc_types.h` and
`mpc_competition.yaml`; the earlier blanket claim that it used unrelated
double-track dynamics was wrong and is withdrawn.

The remaining mismatch is material for faster steering changes:

- Production MPC advances a discrete 25 ms source-command state, including the
  delayed steering command and rate-limited physical steering angle. Its yaw
  response uses midpoint body speed and the next physical angle.
- The original active spatial optimizer used one steering-angle state directly
  for yaw authority and did not model the production command queue or
  physical-angle response. A queue-aware offline candidate was subsequently
  added; its results are summarized below.
- The optimizer recomputes lateral velocity algebraically from speed and yaw
  rate, while production MPC holds the current `v` state inside each 25 ms
  prediction stage. At the next real control update, odometry supplies a new
  estimate.
- The optimizer uses trapezoidal spatial collocation for steering and
  longitudinal commands; production applies zero-order command inputs in
  discrete 25 ms stages.

Thus the fitted yaw residual remains a correction to the production MPC model;
it must not be transplanted into the optimizer's steering-angle equation
without first aligning the state/control semantics. Preserve both yaw-model
comparators and keep the learned residual offline.

Added [the production transition parameter mirror](../../config/racing/racing_vehicle_model.json),
[the C/Python/CasADi production parity verifier](../../tools/racing/verify_optimizer_mpc_model_parity.py),
and [an active optimizer stage audit](../../tools/racing/audit_active_optimizer_stage.py).
The parity verifier configures production C from the frozen MPC YAML and checks
independent Python and CasADi implementations over 1,000 randomized states,
including the full steering and measured curvature ranges. Results are in
[model_parity_shared_transition_v1.json](../../live_runs/racing_model_diagnostics_20261006/model_parity_shared_transition_v1.json):

- Maximum C/Python/CasADi state error: `2.54e-6`.
- Maximum distance increment error: `5.04e-8 m`.
- Maximum longitudinal acceleration error: `1.38e-5 m/s²`.
- C analytic vs CasADi Jacobian error: `2.88e-5` over 932 smooth-branch cases.
- The JSON values match both `mpc_competition.yaml` and compiled C constants.

This verifies production C/Python/CasADi equations and local derivatives, not
accuracy against simulator truth or optimizer parity. The JSON is currently a
fingerprinted parameter mirror, not yet the single runtime source required by
handoff H1.

odometry, or the competition image. The parent trajectory and runtime physics

candidate still had zero samples combining speed >= 6 m/s with |steering| >=

### Current technical conclusion

The missing piece is not another local yaw fit or more open-plane samples. The
active optimizer still uses a continuous spatial transcription, whereas
production MPC advances an exact 25 ms discrete state including queued
commands, actuator slew, and held lateral velocity. Adding a continuous
interpolated queue reduces one-step error, but the accumulated replay proves it
does not reproduce production transitions over a lap. The next optimizer work
must use the production discrete transition (or demonstrate a mathematically
equivalent transcription) and pass a recursive full-lap gate before any
trajectory is map-checked for simulation. The exact C/Python/CasADi stage
equation and parity verifier already exist in
`tools/racing/verify_optimizer_mpc_model_parity.py`; its C/Python/CasADi
parity result does not, by itself, make the spatial optimizer equivalent.

No candidate passed the combined recursive-model and map-clearance gates. The
5.5457 s optimizer estimate is not an actual lap time and must not be presented
as progress. A collision-guarded practice screen was nevertheless run after
the user explicitly requested real-drive evidence; it is recorded below. Do
not use the failed empirical GGV envelope or promote the yaw residual.

## Why progress has stalled, and next evidence-led step

The gap is not primarily a failure to run more solver iterations. The
optimizer's 5.79 s estimate is built on a model that grants more yaw response

## Correction: fixed lateral-acceleration retimer rejected

The exploratory geometric-curvature retimer added during this work used a
constant `9.0 m/s^2` threshold. That value was not estimated from vehicle
measurements and does not represent a verified capability. Its output is
rejected: neither retimed trajectory is an optimizer candidate, and the
reported `5.5969 s` / `5.6413 s` values are only arithmetic kinematic proxies.
The reports now say so explicitly, the CLI no longer supplies a default
threshold, and the tool labels any output as diagnostic-only. The stable P0
trajectory and runtime physics are unchanged.

The active optimizer had the same issue: without an explicit 2-D profile,
`LateralEnvelope` filled its entire speed-by-steering grid with the Pure
Pursuit scalar. That current scalar is `8.0`; an archived v1.3 document said
`6.50`. Both are retained only as legacy curvature-speed shaping settings.
The optimizer field and provenance now identify the fallback as legacy, and
the associated v1.3 docs no longer call it a measured/validated envelope.
The numeric setting and resulting baseline behavior are deliberately
unchanged; this corrects the claim without silently changing the proven P0
controller.

The measured response also remains strongly operating-region dependent. At

full machine-readable result is

There is also prior, more direct evidence that lateral/yaw response changes
with both speed and steering; I should have used it instead of treating the
scalar as a physical limit. The per-speed open-plane surface in
[`OPEN_PLANE_PER_WHEEL_DYNAMICS.md`](OPEN_PLANE_PER_WHEEL_DYNAMICS.md)
trained on 3.0–8.25 m/s source speeds and passed conditional yaw holdouts at
5.0 m/s and 4.5 m/s, while a leave-6.5-m/s-out check missed the measured local
yaw-Jacobian sign in 4/28 cases. That surface was not a full plant: it replayed
measured speed/steering as inputs and held lateral velocity. More importantly,
it failed the practice-bag transfer and the live same-track MPC test (6,617
rejected rollouts, no lap), while the unchanged baseline completed 12 laps at
a 6.0695 s mean in that historical experiment. So the data verify a
speed/steering-varying conditional response, but do not validate that surface
as an optimizer plant or a sustainable lateral-capability boundary.

### Revised modeling/optimizer gate

This supersedes the earlier suggestion above to make another q-gate overlay
and immediately screen it on track. Do not run another static yaw-gate or
constant-lateral-cap variant; the prior per-speed surface already showed why
conditional open-plane accuracy alone is insufficient.

Do not use a single `a_y` threshold, the failed speed-only GGV surface, or
independently measured peaks as a vehicle feasibility model. The optimizer
needs a learned or identified *transition response* conditioned on at least
speed, lateral velocity/yaw history, physical steering and steering rate,
throttle state/slew, and wheel/body-speed mismatch. Any internal state added
for slip/load transfer must be predicted recursively; recorded future sensors
may only label training targets. Fit and compare speed/steering-regime
responses on whole-run splits, then report one-step and recursive errors by
the **joint** operating regime, including independent-run support. Do not
turn marginal speed or steering slices into a fabricated joint capability
surface. The existing speed-only envelope failed practice transfer, and the
existing SUBNET experts trade high-steer accuracy against practice accuracy;
neither is accepted as an optimizer plant.

Before any raceline ranking, the model must improve independent whole-run
state-transition and free-rollout errors in both practice-like and aggressive
steering regimes. Only after that can it score the existing track's feasible
path/speed schedules. No additional broad excitation run is currently
justified by this result; use the existing captures first and request new
data only for a demonstrated unsupported joint transition.
